# Curatorr v0.1.57

## Summary

- **Admin users table play stats fixed** — the table was querying stats using a username derived from the Plex API response, which often differs from the identifier Tautulli stores in `play_events`. The table now iterates observed database IDs and looks up the matching Plex user for display info, so every stat query uses the exact stored value. Users who previously showed "No play history yet" and 0/0/0 plays will now show their correct history.
- **Lidarr stats false positives fixed** — the same identity mismatch caused incorrect Lidarr counts (e.g. 1/1/—) for users who had never used Lidarr automation. Resolved by the same fix above.
- **Lidarr track count now tracked** — when an album is added via Lidarr (automatic or manual), the track count from Lidarr's album data is recorded alongside the album count. The admin users table will now populate the "tracks" column (previously always "—") for adds going forward. Historic adds before this version will continue to show "—".
- **Retry failed Discover adds** — failed "Added for you" items now show a small inline retry icon. Clicking it re-queues the request and immediately triggers the Lidarr queue processor for that user.

## Fixed

- `buildAdminUsersPageData` was iterating `livePlexUsers` (from the Plex API) and deriving a `userId` from `user.username`. Tautulli stores play events under the user's display name (`title`) or a different form. The fix mirrors `buildLocalAdminPreviewData`: iterate `observedPlexUserIds` (actual DB values) and use `buildPlexIdentityLookup` to find the matching live Plex user for display — the raw DB ID is then passed to all stat queries unchanged.
- `resolveLidarrStats` was using `userId` (the mismatched Plex API username) for `lidarr_usage` and `lidarr_artist_progress` queries, causing users with no Lidarr activity to incorrectly show counts when their username matched another user's DB entry. Resolved by the same identity fix.
- Lidarr album add paths (`expandArtistCatalog`, `executeArtistAlbumRequest`, and the manual wizard route in `api-music.js`) now call `recordLidarrUsage` with `usageKey: 'tracks'` and `amount: album.statistics.trackCount` immediately after the album quota is consumed. `resolveLidarrStats` reads the new `tracks_added` column and returns it as a number; `null` is returned when no track data exists (pre-v0.1.57 adds) so the "Tracks not tracked yet" note continues to appear for historic adds.
- `POST /api/music/lidarr/requests/:id/retry` added: resets a failed request to `queued`, records `retried: true` in the detail, and fires `processQueuedRequests` for the owning user immediately. Retry button rendered as a small SVG icon inline with the FAILED badge; errors are surfaced in the page status area rather than overwriting the button.

## Upgrade Notes

- No configuration changes required.
- Recreate the app container after pulling `mickygx/curatorr:latest`.
- Lidarr track counts will only accumulate from this version onwards — existing adds are not backfilled.
