# Curatorr v0.1.96

## Summary

- **Lidarr `new` monitoring works again.** Curatorr now sends Lidarr's two monitoring fields with the enum values each field actually accepts, so selecting `new` no longer makes every artist add fail.
- **M3U import naming stays put.** Previewing an imported `.m3u` or `.m3u8` file no longer pushes the editable playlist-name field down the import dialog.
- **Node 24 CI stays green.** The workflow is pinned to the runtime Node major and uses the Node 24-compatible `better-sqlite3` 12.x addon.

## Fixed

- Fixed Lidarr artist-add payloads for the `new` monitoring mode. `monitorNewItems` keeps `new`, while `addOptions.monitor` now receives `none`, matching Lidarr's separate `NewItemMonitorTypes` and `MonitorTypes` enums.
- Updated the Lidarr add-payload test mock to reject out-of-enum values in either monitoring field with Lidarr's real 400-style error shape, so this class of regression fails in the test suite.
- Fixed the M3U import modal layout so loading the preview list keeps the **New playlist name** input above the preview instead of moving it below the imported-song results.
- Fixed CI failures on Node 24 by keeping the GitHub Actions Node version aligned with the Docker runtime and `better-sqlite3` 12.x.

## Upgrade Notes

- No manual migration is required.
- Existing Lidarr settings are reused. Users who selected `new` monitoring can keep that setting; Curatorr now translates the add payload correctly.
- Rebuild or redeploy Curatorr to pick up the Node 24-compatible dependency set and the playlist import UI fix.
